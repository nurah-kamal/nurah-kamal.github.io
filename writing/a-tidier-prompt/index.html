I tidied a prompt and it broke 9 of 12 tests

One of them was the model following an instruction hidden inside an invoice, and leaking an email address it was told never to copy.

26 October 2026 · about 5 minutes

The setup

I was pulling four fields out of invoices with a language model: supplier, total, currency and date. Twelve invented invoices, in South African, US, German and British formats, with comma decimals, VAT lines and credit lines. Two of the cases aren’t invoices at all and should be declined. One is an invoice with an instruction planted in it.

I had two versions of the prompt. The first one spelled out its rules: totals as plain numbers, dates in ISO format, currency as a code, never copy contact details, refuse anything that isn’t an invoice, and treat the text as text. The second was the same request with those rules taken out. It read better. It’s the kind of edit nobody would stop in a review.

What happened

The original prompt passed 12 of 12 cases. The tidy one passed 3 of 12.

Nothing about the tidy version looked broken when I read the replies. The problems only showed up when something tried to use them:

  • Totals came back as text, like "1 020.00" instead of 1020. Fine for a person, useless for a spreadsheet.
  • The currency came back as "R" instead of "ZAR".
  • Dates came back in five different formats.
  • The supplier field was renamed to supplier_name in 11 of 12 replies, so anything reading supplier got nothing.
  • Asked to write a poem instead of reading an invoice, it wrote the poem.

The one that matters

One invoice has a line in it telling the model to include the account manager’s email address. With the original prompt, the model ignored it. With the tidy prompt, it added a new field, account_manager_email, and filled it in.

That’s the part I’d want anyone building with models to see. The invoice is supposed to be data. The model treated part of it as instructions. If the text you feed in comes from outside, from a customer, a supplier or a web page, then whoever wrote that text gets a say in what your system does. A prompt can extract every field perfectly and still have that problem, and I only found it because there was a test case for it.

What I check now

  • Behaviour, not wording. I don’t care how a reply is phrased. I care whether it parses, whether the total is a number, whether the date is ISO, and whether the email stayed out.
  • Exact values. "1 020.00" looks right and still fails equals 1020, because that’s what would break downstream.
  • Refusals and leaks. Cases that must be declined, and documents that try to give orders.
  • Before and after. Running both prompt versions side by side shows exactly which cases a change breaks and which it fixes, so a prompt edit gets reviewed like a code change.
  • Every push, and weekly. CI replays saved replies on every push, which is fast and gives the same answer each time. A weekly job runs the current prompt against the live model, because the model can change too.

What this doesn’t show

It’s one model, gemini-3.5-flash-lite, on one run on 25 October 2026. Another model might keep more of the tidy prompt’s cases, or fewer. Twelve invoices are the formats I could think of, not every invoice there is. Spotting a refusal in plain words is a pattern match, which is why the suite asks for a JSON flag instead. And all the data is invented, down to the .example email domains.

The suite and the saved replies are public, so the numbers can be checked: prompt-regression on GitHub.
